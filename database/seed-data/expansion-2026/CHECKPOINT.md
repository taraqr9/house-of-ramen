## Process for adding phones (per batch)
1. WebSearch to discover BD-relevant candidates for a brand/price tier NOT already in the catalogue (check against current name list first).
2. WebSearch/GSMArena to verify exact specs for each candidate before writing — do not write from memory alone.
3. Write JSON batch to `database/seed-data/expansion-2026/batch_NN_description.json` (schema: see batch_01-06 for reference).
4. `php artisan phones:import ai_research_2026 --type=manual --chunk=25 --fresh`
5. Check `total_conflicts` in the run output — if >0, investigate immediately (see history below for why this matters).
6. Duplicate check: `Phone::selectRaw('brand_id, LOWER(name) as lname, COUNT(*) as c')->groupBy(...)->havingRaw('COUNT(*) > 1')`.

## Known incidents this project (do not repeat)
- Fabricated a phone that didn't exist ("Redmi Note 13T Pro") — always verify existence, not just specs.
- Wrote near-duplicate phones with wrong specs that overwrote correct existing data (source reliability 72 > existing 55 triggered auto-resolve). Always cross-check candidate names against the CURRENT full catalogue dump before writing, not a stale snapshot.
- **Recurred twice more** ("POCO F6" matched-not-created harmlessly; "Oppo Reno14" overwrote real camera/date data, had to be restored from `phones_seed_21_2025_2026_refresh_batch5.json`). MANDATORY before writing any batch: run the grep-check command below against every candidate model name. Memory of "the list I saw earlier" is not reliable enough at this catalogue size.

```bash
grep -rio "MODEL NAME" database/seed-data/*.json database/seed-data/expansion-2026/*.json
# or, authoritative (DB, not files):

```

## PHASE 0 FIXED: images were not rendering publicly
Root cause: `.env` had `APP_URL=http://localhost` with no port, while the local dev server (`php artisan serve`, started by `composer dev`) listens on :8000. `PhoneImage::url` correctly derives from `Storage::disk('public')->url()` which builds from `config('app.url')` - so every generated image URL pointed at `http://localhost/storage/...` (port 80, nothing listening) instead of `:8000`. Database records were correct and "verified" the whole time; the browser just couldn't reach the URL. This was NOT a data/matching/architecture bug.
Fix: corrected `.env` to `APP_URL=http://localhost:8000`; added a warning comment to `.env.example` for future local setups; added a regression test (`tests/Feature/PhoneImage/PhoneImageAssociationTest.php`) asserting the generated URL is exactly rooted at `config('app.url')` including port, not just "contains the path".
Verified with real headless-Chrome screenshots (`/Applications/Google Chrome.app/Contents/MacOS/Google Chrome --headless --disable-gpu --screenshot=... --window-size=W,H URL`, since no `chromium-cli`/Playwright was available) across: phone detail (Galaxy S24 Ultra, desktop + mobile), homepage, browse grid (21 cards, mix of brands) - all images rendered correctly, no broken-image icons. Also confirmed `curl -I` on the generated URL returns 200 with `Content-Type: image/webp`. Spot-checked publicly-visible phones exist with correct image URLs for Apple, Xiaomi, Redmi, POCO, OnePlus, Vivo, Oppo.
